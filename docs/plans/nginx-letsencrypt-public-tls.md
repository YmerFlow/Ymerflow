# Public TLS via certbot on the frontend nginx (Let's Encrypt)

## Goal & scope

Serve the YmerFlow app, MinIO, and the docker registry publicly over **real Let's Encrypt TLS**,
terminated by the **existing frontend pod's nginx** (no second proxy, no cert-manager, no ingress
controller), with certs obtained/renewed by a **certbot sidecar** and stored on a **persistent
volume** so app redeploys never re-issue. The whole layer is **optional, gated by `config.env`**;
default off = today's behaviour byte-for-byte.

When enabled, all four names resolve to the same public IP (`80.202.232.75`) and share the single
`443` port-forward; the frontend nginx routes them by SNI / Host header:

- `https://redhog.org` → the app (SPA + `/api`, already handled by this nginx).
- `https://s3.redhog.org` → MinIO S3 API.
- `https://console.redhog.org` → MinIO console.
- `https://registry.redhog.org` → docker registry (trusted cert → `docker login registry.redhog.org`
  needs no `insecure-registries`).

One Let's Encrypt certificate with a SAN list covers all four names (HTTP-01, served over the
existing `:80` forward).

## Decision history (how we got here)

Earlier drafts used **ingress-nginx + cert-manager**. Rejected after discussion:

- **cert-manager** is a k8s operator whose HTTP-01 solver creates *ephemeral, randomly-named*
  solver Pods/Services per challenge and needs an **ingress controller** to follow that moving
  target — a static `proxy_pass` can't reach it. It also isn't in the data path, so it adds no
  serving latency itself, but the **ingress-nginx** it pairs with adds an extra proxy hop.
- **certbot** is just a program in a container: it writes the ACME token to a webroot the existing
  nginx already serves, and writes certs to a volume the existing nginx already mounts. No CRDs,
  no controller, no extra proxy. This reuses the one nginx we already run and removes the extra
  hop. Chosen.
- Edge placement: **fold into the frontend pod's nginx** (chosen) vs a dedicated edge nginx pod.
  Folding is truly one nginx and saves the extra app hop; cost is app-deployment-framework changes
  and coupling storage/registry edge exposure to the app's deploy lifecycle (accepted).

## Current state (verified 2026-08-18 on the `mimer` staging host)

**Network / edge**

- Host `mimer` = `192.168.1.179` (iface `eno2`); gw / router = `192.168.1.1`.
- Router: TP-Link Archer C7 v5, OpenWrt 19.07.3, WAN `80.202.232.75`. Reach it from the host with
  `ssh -p 2222 -o HostKeyAlgorithms=+ssh-rsa -o PubkeyAcceptedKeyTypes=+ssh-rsa root@192.168.1.1`
  (busybox `sh`; edit with `uci`).
- **Router port-forwards** (LuCI → Firewall → Port Forwards): `mimer-http` `80→.179:80`,
  `mimer-https` `443→.179:443`, `mimer-ssh` `2221→.179:22`. (The temporary
  `9000/9001/30500` forwards were removed — not needed under subdomains-on-443.)
- **DNS (GoDaddy, via OpenWrt DDNS):** `redhog.org`, `s3.redhog.org`, `console.redhog.org`,
  `registry.redhog.org` all → `80.202.232.75`. The three subdomains were added as DDNS service
  sections (`myddns_s3/console/registry`, `domain='<h>@redhog.org'`) on 2026-08-18 and confirmed
  at the authoritative NS. DNS prerequisite is **satisfied**.

**Cluster / app (all inside minikube, docker driver)**

- minikube publishes NodePorts on the host via `config.env: MINIKUBE_EXPOSE_PORTS="30080 30500
  9000:30900 9001:30901"`, `MINIKUBE_LISTEN_ADDRESS=0.0.0.0`. Editing `MINIKUBE_EXPOSE_PORTS`
  triggers a one-time `minikube delete` + recreate (PVC data survives via host bind-mount).
- **Frontend pod nginx** (`frontend/nginx.conf`, baked into `frontend/Dockerfile`,
  `nginx:alpine`): single `server { listen 80; }` that serves the SPA and reverse-proxies `/api`,
  `/ws/`, `/api/mcp`, `/pgadmin/`, `/headlamp/` to in-cluster services. Runtime config injection
  precedent: `/docker-entrypoint.d/30-headlamp-token.sh` writes `/tmp/headlamp-token.conf`, which
  nginx `include`s.
- **Frontend Deployment + NodePort Service are generated by `yf-deploy-app`**, NOT the static
  `k8s/frontend/*.yaml` (those are the opt-out path). Generators:
  - `backend/services/app_deployment.py :: _apply_frontend()` — builds the Deployment (container
    `port 80`; volume mounts `admin-htpasswd`, `headlamp-token`; readiness `GET / :80`).
  - `backend/services/cluster_providers/nodeport_app_deployment.py :: NodePortAppDeploymentMixin.
    expose_app()` — builds the `NodePort` Service `port 80 → nodePort 30080` (default
    `FRONTEND_NODE_PORT`), and returns `{"url": SERVER_URL or ":<port>"}`.
  - `app_config` (from `config.env` via the generic passthrough,
    `docs/plans/done/generic-backend-config-passthrough.md`) flows
    `yf-deploy-app → deploy_app → apply_app_workloads`, and into `expose_app`. New `PUBLIC_TLS_*`
    keys thread through the same way.
- **MinIO**: ns `minio`, `Service minio` S3 `:9000` + console `:9001`, own self-signed TLS.
  **Registry**: hand-rolled by the `ymerflow-minikube` plugin (`registry_protocol.py`),
  `NodePort 30500`, self-signed TLS + basic auth.
- Relevant `config.env` today: `SERVER_URL=https://redhog.org`, `APP_DOMAIN=redhog.org`,
  `REGISTRY_PUBLIC_HOST=redhog.org`, `STORAGE_ENDPOINT=https://redhog.org:9000`,
  `STORAGE_TLS_SKIP_VERIFY=true`.

## Target architecture

```
              Internet   (redhog.org, s3./console./registry.redhog.org → 80.202.232.75)
                 │
    OpenWrt :80 + :443  (existing DNAT → .179:80 / .179:443)
                 │
          host mimer :80/:443  ──►  minikube NodePorts (add 80:30080, 443:30443)
                 │
   ┌───────────── frontend pod (ns ymerflow) ──────────────────────────────────────┐
   │  nginx (existing, now the TLS edge)                                            │
   │    :80  → ACME /.well-known/acme-challenge (webroot)  +  301 → https           │
   │    :443 → TLS terminate (cert from PVC), route by Host:                        │
   │            redhog.org          → SPA + proxy /api,/ws,/mcp,/pgadmin,/headlamp   │
   │            s3.redhog.org       → minio.minio:9000    (backend-protocol HTTPS)   │
   │            console.redhog.org  → minio.minio:9001                              │
   │            registry.redhog.org → <registry-svc>:5000 (proxy_body_size 0)       │
   │                                                                                │
   │  certbot sidecar (certbot/certbot)                                             │
   │    shares: cert PVC (/etc/letsencrypt)  +  acme webroot emptyDir (/var/www/acme)│
   │    initial `certonly --webroot`; loop `renew`; deploy-hook regen+reload nginx  │
   │    shareProcessNamespace: true  → hook does `nginx -s reload`                   │
   └────────────────────────────────────────────────────────────────────────────────┘
```

## Design decisions

1. **certbot sidecar in the frontend pod**, cert on a **PVC** at `/etc/letsencrypt`. The PVC is the
   crux of "don't re-issue on every redeploy": certs survive pod restarts / app redeploys / even
   `minikube delete` (host bind-mount), so certbot finds a valid cert and no-ops. (Also avoids
   Let's Encrypt rate limits.)
2. **Runtime-generated TLS server block**, mirroring `30-headlamp-token.sh`: a new
   `/docker-entrypoint.d/40-tls.sh` emits the `:443` server (and the `:80` ACME location +
   redirect) into an `include`d file **only when `PUBLIC_TLS` is set AND a cert exists** on the
   PVC. This keeps the image backward-compatible (plain `:80` when TLS is off) and solves the
   first-issuance chicken-and-egg (see bootstrap section).
3. **Subdomains on :443**, one multi-SAN cert, **HTTP-01** over the existing `:80` forward.
   S3 stays **path-style** (already the case — see decision 5), so a single-SAN `s3.redhog.org`
   cert suffices; no wildcard / DNS-01 needed.
4. **nginx re-encrypts to the self-signed MinIO/registry backends** (`proxy_pass https://…` +
   `proxy_ssl_verify off`) — MinIO/registry manifests untouched. (Cleaner alternative — plaintext
   backends — deferred.)
5. **S3 is already path-style — no code change anticipated.** Endpoint today is
   `https://redhog.org:9000` (host:port) and bucket ops work; virtual-hosted-style would target
   `<bucket>.redhog.org:9000` (no DNS) and fail — so path-style is already in effect, and it's a
   property of client+bucket, not the port. Swapping to `https://s3.redhog.org` keeps
   `s3.redhog.org/<bucket>`, covered by the single-SAN cert. **Verify once** after cutover; only if
   some client is found using virtual-hosted-style would `minikube_plugin/storage_protocol.py` need
   `Config(s3={"addressing_style":"path"})`.
6. **In-cluster → registry pulls hairpin through the router — acceptable.** `REGISTRY_PUBLIC_HOST`
   becomes `registry.redhog.org`; minikube's node resolves it to the WAN IP and NATs back through
   OpenWrt. Confirmed OK here → no CoreDNS/hosts override needed.
7. **Gating is two-tier (independent knobs, by design):**
   - *Tier 1 — the TLS machinery* (certbot sidecar, cert PVC, `:443` listener + Service port,
     `40-tls.sh` server blocks, `shareProcessNamespace`) is gated on the single switch
     `PUBLIC_TLS` in `_apply_frontend()`, `expose_app()`, and `40-tls.sh`. `PUBLIC_TLS` empty ⇒
     none of it exists ⇒ today's behaviour byte-for-byte.
   - *Tier 2 — the coupled addressing/publishing values* (`MINIKUBE_EXPOSE_PORTS`,
     `STORAGE_ENDPOINT`, `STORAGE_TLS_SKIP_VERIFY`, `REGISTRY_PUBLIC_HOST`) are **independent
     `config.env` knobs**, deliberately **not** auto-derived from `PUBLIC_TLS`. The operator flips
     them together with `PUBLIC_TLS` per the config.env section below; nothing enforces
     consistency (chosen for flexibility, matching config.env's "explicit value always wins"
     philosophy). ⚠ A half-set state (machinery on, storage still at `redhog.org:9000`) is
     possible and is the operator's responsibility to avoid.
   - Depends on `PUBLIC_TLS` (and the `PUBLIC_TLS_*` keys) reaching `app_config` via the generic
     passthrough — confirm during implementation (open question).

## config.env additions

```sh
# ── Public TLS (optional) ─────────────────────────────────────────────────────
# PUBLIC_TLS=letsencrypt makes the frontend nginx the TLS edge on :443 and runs a certbot
# sidecar that obtains/renews a Let's Encrypt cert onto a persistent volume. Empty/unset =
# no public TLS (today's behaviour: frontend on plain :80 NodePort, MinIO/registry on their
# own self-signed NodePorts).
PUBLIC_TLS=letsencrypt                 # letsencrypt | (empty)
LETSENCRYPT_EMAIL=you@example.com      # ACME account / expiry notices (required when enabled)
LETSENCRYPT_STAGING=true               # true = ACME staging (untrusted, no rate limits) while
                                       # wiring up; flip to false for the real cert.
# Hostnames (leave a subdomain empty to NOT expose that service). App host defaults to APP_DOMAIN.
PUBLIC_TLS_APP_HOST=redhog.org
PUBLIC_TLS_S3_HOST=s3.redhog.org
PUBLIC_TLS_CONSOLE_HOST=console.redhog.org
PUBLIC_TLS_REGISTRY_HOST=registry.redhog.org
# Host NodePort the frontend's TLS listener is published on (mirrors FRONTEND_NODE_PORT for :80).
FRONTEND_TLS_NODE_PORT=30443
```

When `PUBLIC_TLS=letsencrypt`, the operator must **also** flip these **independent** knobs by hand
(Tier 2 — not derived from `PUBLIC_TLS`; documented inline in `config.env.example`):

- `MINIKUBE_EXPOSE_PORTS="80:30080 443:30443 30500 9000:30900 9001:30901"`  (publish host 80/443
  onto the frontend http/https NodePorts; ⚠ triggers a one-time `minikube delete`+recreate)
- `STORAGE_ENDPOINT=https://s3.redhog.org`   (was `https://redhog.org:9000`)
- `STORAGE_TLS_SKIP_VERIFY=false`            (real cert now trusted)
- `REGISTRY_PUBLIC_HOST=registry.redhog.org` (port 443 implied; drop `:30500`)

## Phase 1 — frontend nginx: TLS server blocks + ACME location

In `frontend/` (baked into the image; behaviour still gated at runtime by Phase-2 env + cert
presence):

- Add `/docker-entrypoint.d/40-tls.sh` (sibling of `30-headlamp-token.sh`). When `PUBLIC_TLS` is
  set, it writes `/tmp/tls.conf` (nginx `include`d from the http context) containing:
  - the `:80` server: a `location /.well-known/acme-challenge/ { root /var/www/acme; }` and, for
    everything else, `return 301 https://$host$request_uri;` — **but** keep `:80` serving the app
    too until a cert exists (see bootstrap), and always keep the ACME location.
  - the `:443 ssl` server(s): `ssl_certificate /etc/letsencrypt/live/<primary>/fullchain.pem;`
    `…/privkey.pem;`, one `server_name` per configured host, with the app server reusing the
    existing SPA/`/api`/`/ws`/`/mcp`/`/pgadmin`/`/headlamp` locations, and s3/console/registry
    servers doing `proxy_pass https://minio.minio:9000` etc. with `proxy_ssl_verify off`,
    `proxy_set_header Host $host`, and (registry) `client_max_body_size 0`.
  - The `:443` block is emitted **only if** `/etc/letsencrypt/live/<primary>/fullchain.pem` exists,
    so nginx starts cleanly before the first cert.
- Reference the existing baked `default.conf` (`:80` app server) as-is; `40-tls.sh` layers the edge
  behaviour on top via the `include`, so no rewrite of the shipped config.
- The hostnames + primary cert name come from env (`PUBLIC_TLS_*_HOST`) injected in Phase 3.

## Phase 2 — certbot sidecar + persistent cert volume

- **Volumes (added to the frontend pod in Phase 3):**
  - `letsencrypt` — a **PVC** mounted at `/etc/letsencrypt` in *both* the certbot sidecar and the
    nginx container. Persistent ⇒ no re-issue across redeploys (the whole point).
  - `acme-webroot` — an `emptyDir` mounted at `/var/www/acme` in both containers (challenge files;
    ephemeral is fine).
- **certbot sidecar** (`certbot/certbot`): entrypoint script
  - if no live cert: `certbot certonly --webroot -w /var/www/acme --email $LETSENCRYPT_EMAIL
    --agree-tos --non-interactive [--staging] -d $APP -d $S3 -d $CONSOLE -d $REGISTRY` (skip empty
    hosts), then trigger nginx to pick up the new cert;
  - then loop: `certbot renew` every ~12h with `--deploy-hook` that reloads nginx.
- **nginx reload across containers:** set `shareProcessNamespace: true` on the pod so the sidecar's
  deploy-hook can `nginx -s reload` (or `pkill -HUP nginx`). The hook also re-runs the config-gen
  so the `:443` block appears after the *first* issuance. (Alternative if we don't want shared PID
  namespace: nginx runs a tiny `inotifywait`/periodic `nginx -s reload` on `/etc/letsencrypt`.)

## Phase 3 — app-deployment framework injection (gated on PUBLIC_TLS)

Only when `app_config["PUBLIC_TLS"] == "letsencrypt"`:

- **`_apply_frontend()`** (`backend/services/app_deployment.py`): add to the generated pod
  - the certbot sidecar container (image, env from `PUBLIC_TLS_*`/`LETSENCRYPT_*`, the two volume
    mounts);
  - the `letsencrypt` PVC volume + `acme-webroot` emptyDir, mounted into the nginx container too;
  - a `tls-config`/env wiring so `40-tls.sh` sees the hostnames (env vars on the nginx container);
  - `container_port=443` on the nginx container (keep 80);
  - `share_process_namespace=True` on the pod spec;
  - keep the readiness probe on `:80` (always up).
  Provide the PVC via a `PersistentVolumeClaim` applied here (or in the minikube bootstrap), small
  (a few MiB), `ReadWriteOnce`.
- **`expose_app()`** (`nodeport_app_deployment.py`): add a second Service port
  `443 → nodePort FRONTEND_TLS_NODE_PORT (30443)` alongside the existing `80 → 30080`. Keep the
  422/409 "already allocated" fallback.
- Thread the new keys through the generic `app_config` passthrough (nothing hard-coded; a plugin/
  operator only edits `config.env`).

## Phase 4 — host publishing + config switches

- `MINIKUBE_EXPOSE_PORTS` → publish `80:30080 443:30443` (plus registry/minio as today). One-time
  minikube recreate; schedule with the operator (PVCs incl. the new cert PVC survive).
- Switch `STORAGE_ENDPOINT`, `STORAGE_TLS_SKIP_VERIFY=false`, `REGISTRY_PUBLIC_HOST` per config.env
  section above.

## Phase 5 — backend / config touchups

1. **S3 addressing — verify only** (decision 5); no change expected.
2. **Registry cert baking** — the backend live-fetches the registry TLS cert from
   `REGISTRY_PUBLIC_HOST:30500` to bake into the remote-cluster setup script. With a trusted cert
   on `registry.redhog.org:443`, update the fetch to `:443` or skip baking when
   `PUBLIC_TLS=letsencrypt`. **Verify** the exact path (`settings.registry_public_host`,
   `GET /static/assets/setup-minikube-remote.sh`).

## First-issuance bootstrap (chicken-and-egg)

nginx can't start a `:443` TLS server without a cert, and certbot can't get a cert until nginx
serves the `:80` ACME challenge. Ordering that avoids the deadlock:

1. Pod starts. `40-tls.sh` sees no cert → emits only the `:80` server (app + ACME location; **no**
   forced https redirect yet, so the box stays reachable during issuance).
2. certbot sidecar runs `certonly --webroot` → validates over `:80` → writes cert to the PVC.
3. deploy-hook re-runs `40-tls.sh` (now cert exists → emits `:443` + enables the redirect) and
   `nginx -s reload`.
4. Subsequent pod starts / redeploys: cert already on the PVC → `:443` comes up immediately, certbot
   `renew` no-ops. No re-issue.

(Alternative: ship a throwaway self-signed cert so `:443` always starts, and let certbot replace
it. Avoids conditional include at the cost of a placeholder cert. Decide during implementation.)

## Verification / test plan

1. `LETSENCRYPT_STAGING=true` first. Watch certbot sidecar logs → cert issued to the PVC;
   `curl -vk https://redhog.org` shows the (staging) cert and the app loads.
2. Flip `LETSENCRYPT_STAGING=false`, re-issue, confirm a **trusted** cert: `curl -v https://redhog.org`
   (no `-k`) succeeds; browser padlock clean.
3. App: log in, exercise `/api`, `/ws/`, `/pgadmin/`, `/headlamp/` through `:443`.
4. MinIO: `aws --endpoint-url https://s3.redhog.org s3 ls` (no `--no-verify-ssl`); console at
   `https://console.redhog.org`.
5. **Path-style check:** confirm bucket ops hit `s3.redhog.org/<bucket>`, not
   `<bucket>.s3.redhog.org`.
6. Registry: `docker login registry.redhog.org` (no insecure config), push + pull a test image.
7. Registry pulls in-cluster: trigger a process job / redeploy pulling from `registry.redhog.org`;
   confirm minikube's node pulls succeed (through the router hairpin).
8. **Persistence (the key requirement):** `kubectl rollout restart deploy/frontend` (and a full
   `yf-deploy-app`); confirm certbot logs show *no* re-issue and `:443` serves immediately from the
   PVC.
9. Renewal: force-renew in staging (short cert) and confirm the deploy-hook reloads nginx.

## Rollback

Set `PUBLIC_TLS=` (empty), revert `MINIKUBE_EXPOSE_PORTS` / `STORAGE_ENDPOINT` /
`STORAGE_TLS_SKIP_VERIFY` / `REGISTRY_PUBLIC_HOST`, re-run `runall` / `yf-deploy-app`. The frontend
pod comes back as plain `:80`; the certbot sidecar/PVC are simply not injected. Router forwards and
DNS records are inert when unused.
