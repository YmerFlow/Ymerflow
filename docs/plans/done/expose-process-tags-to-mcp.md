# Expose process-version tagging to MCP clients

## Problem

Process **versions** can be tagged (project-scoped `ProcessTag` rows joined to
versions via `process_version_tags`), and the FlowView can filter by tag. None
of this is reachable from an MCP client, for two independent reasons:

1. **The tag routes are filtered out of the MCP surface.** The MCP server is
   auto-generated by `fastapi_mcp` in `backend/main.py`, which selects routes by
   router tag:

   ```python
   include_tags=["Projects", "Processes", "Datasets", "Environments", "Uploads", "Workspaces"]
   ```

   The tag router (`backend/routers/tags.py`) is grouped under `tags=["Tags"]` —
   not in that list — so every tag route is excluded.

2. **Even if included, the routes are not MCP-quality.** The CRUD routes take an
   untyped `body: Dict` (so the generated tool schema advertises no fields), none
   have an `operation_id` (so tools get ugly auto-names), and docstrings are
   absent (the docstring *is* the tool description). Separately, MCP's process
   listing uses the **terse** `ProcessVersion.to_dict()`, which omits `tags`
   entirely (tags only appear in the `verbose=True` branch at
   `backend/models/process.py:453`) — so a client could write tags but never
   read them back.

Additionally, attaching a tag today is a two-hop dance the frontend already
open-codes in `TagSelector.handleAdd` (`frontend/src/widgets/FlowView/TagSelector.jsx:36`):
find tag by name → if absent, pick a random color from `TAG_COLORS` and create →
attach by id. An MCP caller would have to orchestrate the same create→list→attach
sequence by hand.

## Goals

1. **Read+write tags end-to-end over MCP** — list/create/update/delete
   project tags, and attach/detach tags on a version, all as well-formed MCP
   tools; and surface current tags in the terse process payload so they're
   visible.
2. **Attach by name or id from one method** — tag a version by `tag_name`
   (create-if-absent, with an optional/randomized color) *or* by an existing
   `tag_id`, mirroring the frontend's existing semantics — **without adding a
   second attach endpoint** and **without breaking the current URL**.

## Decisions (settled with the operator)

- **No new attach method.** Modify the **existing** `add_version_tag` handler
  in place: `tag_id` becomes optional, and `tag_name` / `tag_color` are added as
  optional inputs. Backwards compatible — the current
  `POST .../versions/{version}/tags/{tag_id}` URL keeps working unchanged.
- **Full MCP tag exposure** in this plan.
- **Uniform recolor rule (no special case):** whenever `tag_color` is supplied,
  set the resolved tag's color to it — whether the tag was resolved by `tag_id`
  or by `tag_name` (and whether it was just created or already existed). When
  `tag_color` is omitted, keep the tag's existing color (new tags get a random
  palette color).
- **Random color** is drawn from the same palette the frontend uses, mirrored
  into the backend:
  `['#007bff','#28a745','#dc3545','#fd7e14','#6f42c1','#20c997','#e83e8c']`.

## Design

### 1. Make `tag_id` optional on the existing `add_version_tag`

A path segment can't simply become optional, and the existing URL must keep
working. So the **same handler function** is registered on two paths — the
current one (unchanged) plus a body form without the `{tag_id}` segment:

```python
@router.post(".../versions/{version}/tags/{tag_id}", include_in_schema=False)  # legacy URL, frontend
@router.post(".../versions/{version}/tags", operation_id="add_version_tag", summary="Tag a process version")
async def add_version_tag(
    process_id: str, version: int,
    tag_id: Optional[str] = None,           # from path on the legacy route
    body: Optional[VersionTagBody] = None,  # from body on the new route
    ...
):
```

This is **one handler / one operation / one MCP tool** — not a second attach
method. The legacy `/{tag_id}` decorator is a hidden alias (`include_in_schema=False`)
so it stays functional for the frontend but does not create a second OpenAPI
operation or MCP tool. The MCP tool is the body form.

Typed body so the MCP tool schema advertises the fields:

```python
class VersionTagBody(BaseModel):
    tag_id: Optional[str] = Field(None, description="Attach an existing tag by id.")
    tag_name: Optional[str] = Field(None, description="Attach a tag by name, creating it if the project has none by that name.")
    tag_color: Optional[str] = Field(None, description="Hex color for a created tag, or to recolor a matched one. Random from a palette if omitted.")
```

Resolution logic (path `tag_id` and body are merged; body `tag_id` allowed too):

1. Effective `tag_id` = path `tag_id` or `body.tag_id`.
   Exactly one of effective `tag_id` / `body.tag_name` must be given → else `400`.
2. **Resolve the tag:**
   - by `tag_id` → look up by `(id, project_id)`; `404` if absent.
   - by `tag_name` → find `ProcessTag` by `(name, project_id)`; if absent,
     create it with `tag_color` or `random_tag_color()` (matching
     `TagSelector.handleAdd`).
3. **Recolor (uniform, no special case):** if `tag_color` was supplied, set
   `tag.color = tag_color`. (For a just-created by-name tag this is a no-op; for
   any pre-existing tag — resolved by id or by name — it recolors.)
4. **Attach** to the version — the existing insert + `tags_history` "added"
   append + `already_exists` short-circuit is unchanged.

A bare legacy `POST .../tags/{tag_id}` with no body → `tag_color` is `None` → no
recolor: identical to today's behavior.

### 2. Random-color helper + `create_tag` change

```python
TAG_COLORS = ['#007bff','#28a745','#dc3545','#fd7e14','#6f42c1','#20c997','#e83e8c']
def random_tag_color() -> str:
    return random.choice(TAG_COLORS)
```

`create_project_tag` currently defaults an omitted color to the gray
`#6c757d`; change that default to `random_tag_color()`. (Backend `random` is
fine here — the workflow-script randomness restriction does not apply to app code.)

### 3. Type + annotate the CRUD routes for MCP

In `backend/routers/tags.py`, give each MCP-exposed route an `operation_id`, a
real docstring (becomes the tool description), and typed bodies where they take
one:

| Route | method/path | operation_id | body model |
|---|---|---|---|
| list | GET `/projects/{id}/tags` | `list_tags` | — |
| create | POST `/projects/{id}/tags` | `create_tag` | `TagCreate {name, color?}` |
| update | PUT `/projects/{id}/tags/{tag_id}` | `update_tag` | `TagUpdate {name?, color?}` |
| delete | DELETE `/projects/{id}/tags/{tag_id}` | `delete_tag` | — |
| attach | POST `.../versions/{v}/tags` (+ hidden `/{tag_id}` alias) | `add_version_tag` | `VersionTagBody` |
| detach | DELETE `.../versions/{v}/tags/{tag_id}` | `remove_version_tag` | — |

Pydantic models replace the untyped `body: Dict`, using `body.get(...)` reads
mapped to model fields. The attach row is the same existing `add_version_tag`
handler from §1 — listed here only for its `operation_id`/docstring.

### 4. Include the router in MCP

`backend/main.py`: add `"Tags"` to `include_tags`. The legacy `/{tag_id}` attach
path is kept off MCP/OpenAPI via `include_in_schema=False` on that one decorator,
so exactly one attach tool (`add_version_tag`, body form) is generated.

### 5. Surface tags in the terse process payload

`backend/models/process.py`: add `"tags": [t.to_dict() for t in self.tags]` to
the **terse** branch of `ProcessVersion.to_dict()` (today it's verbose-only at
line 453). This is what makes `list_processes` / `get_process` show current tags
to MCP. Confirm the `list_processes` query already eager-loads
`ProcessVersion.tags` (it does — `selectinload(...ProcessVersion.tags)`), so no
N+1.

## Out of scope / non-changes

- **Frontend is untouched.** The legacy `.../tags/{tag_id}` URL still resolves
  (hidden alias on the same handler), so `TagSelector.handleAdd` keeps working
  as is.
- **No new endpoint.** `add_version_tag` is modified in place; only its
  parameters change (`tag_id` optional, `tag_name`/`tag_color` added).
- No change to `tags_history`, the join table, or the filter logic.

## Files touched

- `backend/routers/tags.py` — Pydantic models, `operation_id`s, docstrings,
  `random_tag_color`; `add_version_tag` gains the body form + hidden `/{tag_id}`
  alias and the by-name find-or-create branch.
- `backend/main.py` — add `"Tags"` to `include_tags`.
- `backend/models/process.py` — tags in terse `to_dict()`.

## Verification

- MCP: with an `apk_` key scoped to a project — `create_tag` (omit color →
  non-gray), `add_version_tag` by `tag_name` (creates), again by same name
  (reuses; recolors iff color given), `list_processes` shows the tag,
  `remove_version_tag` removes it.
- REST/frontend regression: the legacy `.../tags/{tag_id}` attach/detach URLs
  and the FlowView tag filter still work unchanged.
- `require_project_member` still gates writes; `resolve_project_for_read` gates
  `list_tags`.
